# Tool Naming Conventions

The tool surface is specified in `docs/unified-tools/` (30 tools) and
generated by `scripts/build_unified_tool_specs.py`. Names, descriptions,
annotations and `meta` are edited there, never in handlers.

## Core Naming Pattern

`[category]_[verb]` or `[category]_[verb]_[object]`, lower snake_case,
stable across releases (renames are breaking changes; see `mcp-server.md`).

## Categories and Prefixes

| Category | Prefix | Tools |
|----------|--------|-------|
| Generic resource tools | `m365_` | `m365_list`, `m365_get`, `m365_search`, `m365_get_content`, `m365_create`, `m365_update`, `m365_move`, `m365_delete` (dispatch on `resource`) |
| Email | `email_` | `email_create_draft`, `email_send`, `email_reply`, `email_forward`, `email_folder_mark_all_read`, `email_folder_empty`, `email_rule_manage` |
| Calendar | `calendar_` | `calendar_create_event`, `calendar_update_event`, `calendar_respond`, `calendar_forward`, `calendar_find_availability` |
| OneDrive | `drive_` | `drive_upload`, `drive_copy`, `drive_share` |
| Accounts | `account_` | `account_list`, `account_auth_begin`, `account_auth_complete` |
| Administration | `admin_` | `admin_cache_get`, `admin_cache_invalidate`, `admin_server_info`, `admin_reauth_schedule` |

Resource names (the `resource` enum) are identical across tools: `email`,
`email_folder`, `email_rule`, `event`, `calendar`, `contact`,
`contact_folder`, `drive_item`, `operation`.

A new tool gets a dedicated name only when its intent, safety level,
confirm rule, retry semantics or result shape differ from an existing tool
(concept §4). Otherwise extend the generic tool with a resource.

## Safety Metadata

Every tool carries MCP annotations and a `meta` block:

```json
{
  "annotations": {
    "title": "Send Email",
    "readOnlyHint": false,
    "destructiveHint": false,
    "idempotentHint": false,
    "openWorldHint": true
  },
  "meta": {
    "category": "email",
    "tier": "core",
    "safety_level": "dangerous",
    "confirm": "always",
    "confirm_rule": "Always required."
  }
}
```

| `safety_level` | `readOnlyHint` | `destructiveHint` | Meaning |
|---|---|---|---|
| `safe` | `true` | `false` | Reads only |
| `moderate` | `false` | `false` | Changes your own data |
| `dangerous` | `false` | `false` | Sends, notifies or shares with other people |
| `critical` | `false` | `true` | Destroys data |

`meta.confirm` is `never`, `always` or `conditional` (with
`confirm_rule`). `dangerous` and `critical` tools have a `confirm`
parameter that defaults to `false`; the server refuses the call unless it
is `true`. `meta.tier` (`core`, `extended`, `admin`) controls exposure via
`M365_MCP_TOOLSETS`.

## Description Template

No emoji and no safety prose prefixes; safety lives in annotations and
`meta`. Descriptions are written for the model and follow:

1. **What it does**, in one sentence naming the objects it acts on.
2. **Use when**: the situation this tool is for.
3. **Do not use**: the neighbouring tool to use instead, by name.
4. **Confirmation**, when `confirm` applies: "Requires confirm=true after
   the user approves ...".
5. **Returns**: what comes back (for lists, mention `next_cursor`).

Example (`m365_list`): "Browse items of one type in a known place: ...
Use this when you know where to look. Use m365_search to find items by
text, and m365_get when you already have an ID. Returns compact items plus
next_cursor for more."

Parameter descriptions are required for every parameter; closed sets are
enums, numbers are bounded and objects are closed
(`additionalProperties: false`). `tests/test_unified_tool_specs.py`
enforces these rules and the definition token budgets.
